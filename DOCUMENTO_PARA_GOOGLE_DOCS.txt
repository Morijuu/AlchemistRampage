1. INTRODUCCIÓN Y OBJETIVOS

1.1 Contexto

AlchemistRampage es un juego 2D en Unity donde el jugador controla a un alquimista que combina diferentes tipos de balas para derrotar enemigos. El proyecto necesitaba sistemas fundamentales para gestionar la mecánica central del juego: la combinación de proyectiles.

1.2 Objetivos de la Recuperación

Objetivo Principal: Implementar sistemas de programación que demuestren comprensión de gestión de datos, arquitectura de software y mecánicas de juego complejas.

Objetivos Específicos:

• Sistema de Inventario: Permitir al jugador acumular múltiples balas y gestionar su colección de forma eficiente.

• Sistema de Combinación: Crear un mecanismo que permita combinar dos tipos de balas para obtener nuevos tipos, con lógica de validación.

• Menú de Recetas: Desarrollar una interfaz visual que muestre todas las combinaciones disponibles, accesible mediante TAB sin pausar el juego.

• Sistema de Estadísticas: Rastrear métricas del jugador durante la partida y mostrarlas al terminar.

3. SISTEMA DE INVENTARIO

3.1 Objetivo

Permitir al jugador acumular y gestionar múltiples balas de diferentes tipos, proporcionando métodos para añadir, obtener y manipular el inventario.

3.2 Arquitectura

El sistema utiliza el patrón Singleton para garantizar una única instancia del inventario en la aplicación.

3.3 Código Principal (BulletInventory.cs)

public class BulletInventory : MonoBehaviour
{
    public static BulletInventory Instance { get; private set; }

    private Dictionary<BulletType, int> bullets = new();

    private void Awake()
    {
        Instance = this;
    }

    public void AddBullet(BulletType bulletType, int amount = 1)
    {
        if (bullets.ContainsKey(bulletType))
            bullets[bulletType] += amount;
        else
            bullets[bulletType] = amount;
    }

    public int GetBulletCount(BulletType bulletType)
    {
        return bullets.ContainsKey(bulletType) ? bullets[bulletType] : 0;
    }

    public bool UseBullets(BulletType bulletType, int amount)
    {
        if (GetBulletCount(bulletType) >= amount)
        {
            bullets[bulletType] -= amount;
            return true;
        }
        return false;
    }
}

3.4 Características Clave

• Uso de Dictionary para almacenamiento eficiente O(1)
• Singleton pattern para acceso global
• Métodos de validación antes de consumir munición
• Escalable para futuros tipos de balas

3.5 Decisión Técnica

¿Por qué Dictionary? Proporciona búsqueda y acceso en tiempo O(1), mejor que List. Cada tipo de bala es única, no hay duplicados en la clave.

4. SISTEMA DE COMBINACIÓN DE BALAS

4.1 Objetivo

Implementar un sistema que permita combinar dos balas de diferentes tipos para obtener una nueva bala, con validación de disponibilidad y consumo automático.

4.2 Diseño de Combinaciones

Las combinaciones posibles están predefinidas en BulletInventory.cs.

public static List<(BulletType a, BulletType b, BulletType result)> GetAllRecipes()
{
    return new List<(BulletType, BulletType, BulletType)>
    {
        (BulletType.Regular, BulletType.Heavy, BulletType.Area),
        (BulletType.Heavy, BulletType.Bouncy, BulletType.Frag),
        (BulletType.Area, BulletType.Target, BulletType.Chain),
        // ... más combinaciones
    };
}

public bool TryCombine(BulletType a, BulletType b)
{
    var recipe = GetRecipe(a, b);
    if (recipe == null) return false;

    if (!UseBullets(a, 1) || !UseBullets(b, 1)) return false;

    AddBullet(recipe.Value.result, 1);
    return true;
}

4.3 Validaciones

• Verificar que ambas balas existen en el inventario
• Verificar que hay al menos 1 de cada tipo
• Consumir ambas balas ANTES de crear la nueva
• Validar que la combinación existe en la tabla de recetas

5. MENÚ DE RECETAS

5.1 Objetivo

Crear una interfaz visual accesible que muestre todas las recetas disponibles sin pausar el juego, permitiendo al jugador consultar combinaciones mientras juega.

5.2 Características del Menú

• Accesible mediante tecla TAB sin pausar el juego
• Toggle: abre/cierra con TAB, cierra con ESC
• Ubicado en esquina superior derecha (no interfiere con juego)
• Muestra todas las recetas con colores por tipo de bala
• Hint de ayuda visible cuando está cerrado

5.3 Código de Control (RecipeMenuToggle.cs)

public class RecipeMenuToggle : MonoBehaviour
{
    private void Update()
    {
        if (Input.GetKeyDown(KeyCode.Tab))
        {
            gameObject.SetActive(!gameObject.activeSelf);
        }

        if (gameObject.activeSelf && Input.GetKeyDown(KeyCode.Escape))
        {
            gameObject.SetActive(false);
        }
    }
}

5.4 Nota sobre la Implementación

TRANSPARENCIA SOBRE IA: La creación de los elementos de UI (Canvas, Panels, Texts) fue generada asistida por IA en UIManager.BuildRecipeCanvas(). Sin embargo, la lógica de control (toggle con TAB, gestión de estados, integración con el sistema de recetas) es programación pura basada en comprensión de arquitectura de software. La IA solo aceleró la creación visual, no la lógica crítica.

6. SISTEMA DE ESTADÍSTICAS

6.1 Objetivo

Rastrear métricas importantes del juego durante la partida y mostrarlas al terminar, proporcionando retroalimentación al jugador sobre su desempeño.

6.2 Métricas Rastreadas

Métrica              | Descripción                         | Fuente
Daño Realizado       | Daño total infligido a enemigos   | BulletScript.cs
Daño Recibido        | Daño total recibido por jugador   | Health.cs
Daño Curado          | Vida total recuperada             | Health.cs
Zombies Matados      | Número de enemigos eliminados     | Health.cs
Tiempo de Partida    | Duración total del juego          | GameStats.cs

6.3 Código del Sistema (GameStats.cs)

public class GameStats : MonoBehaviour
{
    public static GameStats Instance { get; private set; }

    public float damageDealt = 0f;
    public float damageTaken = 0f;
    public float damageHealed = 0f;
    public int zombiesKilled = 0;
    private float startTime = 0f;

    private void Awake()
    {
        Instance = this;
        startTime = Time.time;
    }

    public void AddDamageDealt(float damage) => damageDealt += damage;
    public void AddDamageTaken(float damage) => damageTaken += damage;
    public void AddDamageHealed(float damage) => damageHealed += damage;
    public void AddZombieKilled() => zombiesKilled++;

    public float GetGameDuration() => Time.time - startTime;
}

6.4 Puntos de Rastreo en el Código

En BulletScript.cs (cuando bala impacta):
    health.TakeDamage(data.damage, transform);
    if (!isEnemyBullet)
        GameStats.Instance?.AddDamageDealt(data.damage);

En Health.cs (cuando jugador recibe daño):
    if (isPlayer)
        GameStats.Instance?.AddDamageTaken(damage);

En Health.cs (cuando se cura):
    public void Heal(int amount)
    {
        currentHealth += amount;
        GameStats.Instance?.AddDamageHealed(amount);
    }

En Health.cs (cuando enemigo muere):
    if (CompareTag("Enemy"))
    {
        AudioManager.Instance?.PlayZombieDeath();
        GameStats.Instance?.AddZombieKilled();
    }

7. PROBLEMAS Y SOLUCIONES

7.1 Problema: Conflicto de Diccionarios en Estadísticas

PROBLEMA: Los paneles de Victoria y Derrota compartían el mismo diccionario statTexts, causando que al mostrar un panel se actualizaran los textos del otro panel con valores incorrectos.

SOLUCIÓN: Crear dos diccionarios separados (gameOverStatTexts y winStatTexts) y pasar el diccionario correcto a cada método AddStatLine(). Cada panel ahora actualiza solo sus propios elementos.

7.2 Problema: GameStats retornaba "N/A"

PROBLEMA: Inicialmente intenté usar reflexión para acceder a GameStats.Instance, lo que falló porque System.Type.GetType("GameStats") no encontraba la clase.

SOLUCIÓN: Cambiar de reflexión a acceso directo usando FindFirstObjectByType<GameStats>() y además asegurar que GameStats existe en Start() del UIManager.

7.3 Problema: UI del Menú de Recetas Corrupta

PROBLEMA: Intenté crear la UI del menú de forma estática en el editor, pero la renderización fallaba mostrando elementos distorsionados.

SOLUCIÓN: Cambiar a crear la UI dinámicamente en runtime con Canvas.renderMode = ScreenSpaceOverlay, utilizando anchors y offsets simples.

8. DECISIONES TÉCNICAS

8.1 Patrón Singleton para Managers

Se utilizó el patrón Singleton para BulletInventory, GameStats y UIManager porque:

• Se necesita acceso global desde múltiples scripts
• Solo debe existir una instancia en la aplicación
• Simplifica el código eliminando necesidad de búsquedas constantes

8.2 Dictionary vs List para Inventario

DECISIÓN: Dictionary<BulletType, int> en lugar de List<BulletData>

RAZÓN: O(1) de búsqueda vs O(n). Cada tipo de bala es único, no hay necesidad de duplicados. La clave es el tipo, el valor es la cantidad.

8.3 Crear UI en Runtime vs Editor

DECISIÓN: UI dinámica en runtime para el menú de recetas

RAZÓN: Evita problemas de compatibilidad con diferentes resoluciones y permite que el menú se genere automáticamente basado en las recetas disponibles.

8.4 Actualizar Estadísticas al Mostrar Panel

DECISIÓN: Obtener valores en ShowWin()/ShowGameOver(), no en BuildCanvas()

RAZÓN: Los valores se calculan durante la partida. Si los obtenemos cuando se crea el Canvas, obtendremos valores vacíos (0).
